OPEN-NET-AGENT // 多节点证据检索

跨多个节点找证据，
再给出有出处的答案。

你问一个问题，它先决定去哪些节点找（每个节点只持有一部分资料），在各节点召回段落，挑出能互相接上的那几段，读出答案，并标出用了哪几段。不是另一个聊天框，也不要求把所有资料塞进同一个上下文。

跨节点取证资料分散在不同节点/分片时，先路由、再分头召回。场景：A 院有病历、B 院有检验报告，问“有没有用药禁忌”
多跳接链第一段只给出桥梁实体，第二跳带着它去另一节点找属性。场景：“这位作曲家的出生城市现在人口多少” → 作曲家 → 城市 → 人口
答案带出处每条结论都落到具体段落：标题 + 所在节点 + 候选排名。场景：合规/审计要求每个结论都能回到原文核对
可评测、可比较同一口径（both@5、题目聚类 bootstrap CI，即按题重采样估区间）量化每次改动。场景：换检索深度/路由策略前后，跑同一批题看差值
看一道真题怎么跑 ↓ 它不擅长什么 自己问一题

诚实优先 · 限制也写进来
擅长 · WHAT IT IS GOOD AT

需要跨节点/跨分片找证据、且有明确段落可引用的多跳问题。答案能指到“第几段、哪个节点”。

已验证：dmqa_dev 100 道多跳题、3 个合成分片节点，both@5 = 0.72；PubMed 87 条 claim 的检索 Hit@1 = 1.00。

不适用 · NOT A FIT

单跳事实、闲聊、写作生成：普通搜索或 LLM 更快更便宜。需要“比较两段数值再下结论”的比较题也弱（Hotpot comparison both@2 = .199，bridge = .547）。

读出限制：本页答案是抽取式（选句 + 抽 span），不做改写；需要综合多段写成一段话时，它不是生成器。

延迟与预算 · LATENCY

单题召回 ~0.14s（k=10，含查询编码，本机）；本页 trace 的读段（20 候选 → top-5）约 0.5s，单线程 Python、未优化。端到端还要加后端与网络。

预算：B=3 已测过，递增收益不足，默认不加；k=20 是可选高预算档，不是默认。

离 oracle 多远 · DISTANCE TO ORACLE

候选池上限 .78 → 实际选中 .72，差 6 个点卡在“选错/读出”。三项可加总分解：命中 .78 / 节点未查 .11 / 深度不足 .11。

样本不足：跨节点只有 33 题，bootstrap CI 半宽约 ±.07，不能支持“节点更多更好”这类结论；多节点 33 题样本不足，D1 路由改进（.720→.790）仍只是实验结论、未改默认。
