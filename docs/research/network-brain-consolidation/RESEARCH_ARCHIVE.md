## 0. 先读这一页

### 0.1 一句话结论

这条链路已经能**稳定找到证据**（集合级 both@5 = 0.790），但**还不能稳定把证据变成答案**（98 题整体 exact-match = 7.1%）。三态 gate 让系统在 46 道题上诚实地说“不够”，代价是覆盖率减半；当前最大的缺口不在检索，而在读出。

### 0.2 当前默认链路

```
问题
 → D1 稠密节点路由：query 编码一次，按每节点 max cosine 取独立 top-2（B=2）
 → 每节点稠密召回 k=10（bge-small-en-v1.5），两节点共 20 个候选段落
 → 11 维 fast verifier 打分
 → 集合级 pair head 贪心选 K=5 段
 → 抽取式读出（按 qtype 分支抽 span）
 → 三态判定：answered / insufficient / conflict
```

### 0.3 两个数字不能混着说

| 口径 | 数值 | 样本 | 衡量什么 |
|---|---:|---:|---|
| 集合级 **both@5** | **0.790**（95% CI 0.71–0.87） | 100 题 | 两个 gold 段落是否都进入选中的 K=5，**衡量“找证据”** |
| **exact-match 答案准确率**（整体） | **7/98 = 7.1%**（95% CI 3.5%–14.0%） | 98 题 | 抽出的答案串与 gold 精确匹配，**衡量“答对”** |
| exact-match（answered 子集） | 7/48 = 14.6%（95% CI 7.2%–27.2%） | 48 题 | 只在不弃答的题上算，**会掩盖覆盖率下降** |

**both@5 高 ≠ 答案对。** 0.790 说明证据基本找得到；7.1% 说明读出几乎没把证据用起来。任何把这两个数字放在一起比较的叙述都是错的。另外注意样本差：both@5 用 100 题，exact-match 用 98 题（线上接口拒绝 >180 字符的问题，跳过 2 题）。

### 0.4 最大缺口

46 道 `insufficient` 中：

- **(a) 语料里确实没有答案 = 0**
- **(b) 有答案但抽取失败 = 46（100%）**
- **(c) 判据误杀 = 0**

其中 **27/46（58.7%）是读出器根本没有对应答案形式的分支**（19 道 `other` + 8 道 yes/no），**37/46（80.4%）的 gold 字面已经在选中的段落里**。详见第 6 节与 12 例人工核对表。

## 1. 口径词典

### 1.1 数据与切分

- **数据集**：HotpotQA validation 子集，`dmqa_dev`（3975 段，100 test / 300 train）；每条问题两个 gold 支撑段。
- **节点**：3 个主题节点（电影/剧集 1971 段、体育/音乐 918 段、人物/政治 1086 段），每个 title 唯一落在一个节点。
- **跨节点题**：100 题中只有 **33 题**的两个 gold 分属不同节点；其余两段在同一节点。所有跨节点结论都受这 33 题限制。
- **预算**：B=2（默认）、B=3（对照）；每节点召回深度 k=10（默认）、k=20（高预算档）；选中集合 K=5。
- **长题**：2 道 >180 字符的题在线上三态评估中被跳过，故 exact-match 的分母是 98。

### 1.2 指标定义

| 指标 | 定义 | 用途 |
|---|---|---|
| `both@2` | 两个 gold 段都进入前 2 | 严格证据命中 |
| `both@5` | 两个 gold 段都进入前 5 | **主证据指标** |
| `recall@5` | 两个 gold 段中进入前 5 的比例（按段计） | 单段召回 |
| `MRR` | 第一个 gold 段的倒数名次 | 排序质量 |
| `ceiling` / 池上限 | 两个 gold 都在已查询节点的候选池里（不看最终 K=5） | 检索器上限 |
| `ws` | workspace 逐候选竞争选出的 top-5 | 旧读出/选择方式 |
| `set` | 集合级 pair head 贪心选出的 top-5 | 当前默认选择器 |
| `node_recall` | 两个 gold 所在节点是否都被 B=2 路由查到 | 路由覆盖 |
| exact-match | 抽出答案串与 gold 精确匹配（先剥离非数字字符再比） | **答案正确率** |
| `answered` 子集准确率 | 只在 status=answered 上算 exact-match | 精确率，须与覆盖率同报 |
| 整体准确率 | 在全部 98 题上算 exact-match，弃答记为错 | 真实端到端 |
| 弃答率 | `insufficient` / 全部 | 覆盖率代价 |

### 1.3 区间与判定

- **单比例**：Wilson 95% 区间（本文中 7/98、7/48、46/98、9/58 等）。
- **配对差**：按题目聚类的 bootstrap，1000 次重采样；`[a, b]` 为 95% CI。
- **±0.07 规则**：2026-11-10 起约定，配对差 CI 半宽在 ±0.07 内不解读差异，只记“方向一致/噪声内”。这是一条**保守判据**，不是统计显著性本身。
- **n 的含义**：`n=100` 指 100 道 test 题；`n=300` 指 100 题 × 3 seeds 的评测单元；`n=250` 指 250 道 test 题（E9/E11/E12 的 1000 题数据集）。文中逐处标注。

## 3. 阶段记录：结论 → 证据 → 状态

### 3.0 前史：E1–E7 pilot（为什么会有后面这些实验）

**当时的想法**：把 5 个节点各自检索的结果放进一个容量受限的 global workspace，用 verifier + novelty + coverage + coalition 竞争，应该能超过“把候选拼起来再排序”的 flat ensemble。

**证据（n=100，5 节点，100 distractors/节点）**：

| 方法 | both@2 | both@5 |
|---|---:|---:|
| 最佳单节点 | 0.00 | 0.00 |
| 集中式检索（510 段） | 0.20 | 0.39 |
| flat verifier | 0.39 | 0.53 |
| **NBPW workspace** | **0.40** | **0.55** |
| no verifier | 0.23 | 0.46 |

- workspace 比 flat verifier 只高 **+0.02**；E1b 的公平对照（去掉跨节点 agreement 特征）是 **+0.01，95% CI [0.00, 0.03]**，1 win / 0 losses。
- 消融：`no_novelty` 0.53、`no_coverage` 0.53、`no_coalition` 0.52，与完整版 0.55 的差都在噪声内。

**状态**：**已推翻**（“一次性 workspace 重排是网络级增益”）。真正的杠杆是 verifier 和节点选择，不是 workspace 规则。这一条推翻了整个项目的初始假设，也是后面所有实验的起点。

### 3.1 主动证据选择（E8–E11）

**当时的问题**：既然 workspace 不行，钱应该花在“查哪些节点”上。B 个节点预算下，能不能用节点画像/学习打分器显著超过随机？

**做了什么**：E8（100 题，B=1/2/3/5）、E9（1000 题，250 test）、E10（10 节点）、E11（学习型 node scorer，400 训练题 rollout）。

**证据**：

| 实验 | 对比 | 结果 | 样本 / CI |
|---|---|---|---|
| E8 | active vs random，B=2，both@5 | 0.247 vs 0.090 | n=100；无 CI |
| E8 | active vs random，B=3 | 0.367 vs 0.217 | n=100；无 CI |
| **E9** | active − random，B=2 | **+0.224** | n=250；95% CI [0.156, 0.292]，71 win / 15 loss |
| **E9** | active − random，B=3 | **+0.236** | n=250；95% CI [0.164, 0.308]，80 win / 21 loss |
| E10 | active vs random，B=4，10 节点 | 0.303 vs 0.113 | n=100；无 CI |
| **E11** | learned − profile，B=2 | **+0.108** | n=250；95% CI [0.040, 0.180] |
| E11 | learned，B=2 / B=3，both@5 | 0.400 / 0.496 | n=250；vs oracle 0.819 / 0.672 |

**状态**：**已确立**。主动选择在 100 题、250 题、10 节点三种设置下都为正，E9/E11 的 CI 不含零。注意：B=2 时 active 只用约 39% 的全节点字节，却拿到全节点 both@5 的 49%；B=3 拿到 66% / 59% 字节。**这是效率增益，不是“更多算力换更多分”。**

**同时留下的负结果**：`oracle` 在 B=3（0.672）反而低于 B=2（0.819），因为候选变多、K=5 被稀释。**“加预算”不是单调的**，这一条后来在 D1 阶段再次出现。

### 3.2 node-local BM25 hybrid（2026-11-06）

**当时的问题**：节点画像（profile）用 TF-IDF 统计量手写；能不能把每节点的 BM25 分数并进去，让节点选择更准？

**做了什么**：在同一批 100 题 × 3 seeds 上比较 `active_orig`（原画像）、`active_bm25`、`active_bm25strong`、`active_hybrid`（画像 + BM25 信号）。另试了“dense profile”（用 TF-IDF 余弦冒充稠密相似度）。

**证据**（both@5）：

| 策略 | B=2 | B=3 |
|---|---:|---:|
| random | 0.090 | 0.217 |
| active_orig | 0.247 | 0.367 |
| active_bm25 | 0.357 | 0.477 |
| active_bm25strong | 0.363 | 0.480 |
| **active_hybrid** | **0.400** | **0.487** |
| oracle | 0.783 | 0.673 |

- hybrid 比 orig 高 **+15.3pt（B=2）/+12.0pt（B=3）**；后续差距分解报告在 n=300 上复现 hybrid B=2 = 0.397 [0.323, 0.473]，与 0.400 一致。
- **dense profile 失败**：`active_dense` 在 B=2/B=3 与 random 完全相同（0.090 / 0.217）。原因是 TF-IDF 余弦没有跨节点语义信号，节点打分退化为常量。

**状态**：hybrid 本身 **已确立**（方向在 3 seeds + 后续 n=300 复现；该文件未给配对 CI）。dense profile **未成立**（一次尝试即被否掉，不是“曾经相信”）。

### 3.3 差距分解（2026-11-09）

**当时的问题**：hybrid 到 oracle 还差 0.39（B=2），这段差距到底该投池子、选择器还是读出？

**做了什么**：逐题记三个布尔量，严格恒等分解：

```
1 − both@5 = P(池取不到) + P(池可取但节点没查) + P(节点查了但读出/选择失败)
```

**证据**（n=300，100 题 × 3 seeds；括号为题目聚类 bootstrap 95% CI）：

| 策略 | B | both@5 | 池 | 选择器 | 读出 |
|---|---:|---:|---:|---:|---:|
| hybrid | 2 | **0.397 [0.323, 0.473]** | 0.120 | **0.457 [0.383, 0.527]** | 0.027 |
| oracle | 2 | 0.787 [0.710, 0.860] | 0.120 | 0 | 0.093 |
| hybrid | 3 | 0.503 [0.413, 0.593] | 0.120 | 0.237 | 0.140 |
| oracle | 3 | 0.680 [0.593, 0.763] | 0.120 | 0 | 0.200 |

- B=2 的误差构成：**选择器 75.7%**、池 19.9%、读出 4.4%。
- B=2 的绝对天花板 **0.787**；其中 0.213 是任何选择器都碰不到的地板（池 0.120 + 读出 0.093）。
- B=3 选择器占比降到 47.6%，读出升到 28.2%；oracle B=3 反而低于 B=2。

**状态**：分解恒等式 **已确立**（8 个策略×预算组合残差为 0，逐题严格成立）。但“选择器是最大瓶颈”这条**只对 B=2、5 节点随机切分成立**；后来主题切分下池损失的主因变成节点内深度（见 3.6），这条被部分修正。

**当时的误读（后来被推翻）**：“B=2 的 selector 桶里 76% 是节点选择，所以完美选择器能多拿 +0.390。” 实际上 +0.390 里大部分是**段落选择**的 headroom，不是节点选择；11-10 的深度报告进一步证明，在 3 主题节点下只有 3pt 来自“gold 节点没被查”，其余是深度。详见 4.3。

### 3.4 verifier 融合读出（2026-11-09）

**当时的问题**：旧 verifier 只有 11 维词面特征。能不能加 NLI 蕴含 + 抽取式 QA 置信度，把“哪一段真正回答了问题”识别出来？

**做了什么**：预计算 9,787 个问题×段落对的 NLI/QA 信号（126.8 ms/对，MPS），训练 A（NLI）、B（答案侧）、C（26 维融合）、RRF 四种读出，候选集与选择器完全固定。

**证据**（all-nodes both@5，n=300）：

| 读出 | both@5 | 相对旧 |
|---|---:|---:|
| 旧 heuristic verifier | 0.517 [0.460, 0.573] | — |
| A · NLI 蕴含 | 0.477 [0.423, 0.530] | −4.0pt |
| B · 答案侧抽取 + 投票 | 0.380 [0.327, 0.437] | −13.7pt |
| **C · 融合（旧+A+B）** | **0.677 [0.620, 0.727]** | **+16.0pt** |
| C' · 轻量 RRF | 0.573 [0.510, 0.630] | +5.7pt |

**但端到端几乎不动**：

| 条件 | 旧 | C | Δ | 池内可达 |
|---|---:|---:|---:|---:|
| hybrid B=2 | 0.390 | 0.403 | **+1.3pt** | 0.423 |
| hybrid B=3 | 0.503 | 0.557 | +5.3pt | 0.643 |
| oracle B=2 | 0.780 | 0.827 | +4.7pt | 0.880 |

- 成本：**126.8 ms/候选对 vs 0.97 ms/对，慢 131×**；B=2 每问约 10 对 → +1.27 s/query。
- 多节点复现时融合没有兑现 +16pt（最好 +2pt），在 replica 上还会因训练 head 正样本太少而崩（0.36 → 0.09）。

**状态**：融合读出在“候选池完整”时 **已确立**（+16pt，CI 不重叠）；作为默认 **已推翻**（端到端 +1.3pt、131× 开销、多节点衰减）。最终保留为 `NBPW2_READOUT=fusion` 的 opt-in 档，默认 `fast`。

**被保留的负结果**：NLI 直接把问句当 hypothesis 喂 MNLI 是方向错的（AUC 0.444，单独排序 both@5 0.023）。MNLI 需要陈述句；要做 NLI 必须先做问句→陈述句改写。这一条不是“没调好”，是结构性错误。

### 3.5 集合级选择器（2026-11-10）

**当时的问题**：逐候选独立打分的 workspace 无法决定“哪两段应该一起出现”。能不能用 pair/set 条件化打分，把桥接段拉进来？

**做了什么**：12 维 pairwise 特征（rel_c、rel_anchor、bridge_caps、title_in_anchor、rare_overlap、novelty、cov_gain、ans_dup、node_diff、rank、len 等），pair（条件于第一跳 anchor）和 set（条件于所有已选段）两种打分；选择器固定，读出 fast。

**证据**（n=300，100 题 × 3 seeds；CI 为题目聚类 bootstrap）：

| 条件 | workspace | set | Δ |
|---|---:|---:|---:|
| all-nodes（25 候选） | 0.520 | **0.763** | **+24.3pt**（CI 不重叠） |
| hybrid B=2（10） | 0.390 | 0.417 | +2.7pt（**CI 完全重叠**） |
| hybrid B=3（15） | 0.503 | **0.617** | **+11.3pt** |
| oracle B=2 | 0.780 | **0.860** | **+8.0pt** |

- 收益全部来自 bridge 题型：workspace 0.377 → set 0.675；comparison 已 100%，没有空间。
- 防伪消融：`set_nobridge` 掉回 0.540，`set_nocov` 0.760 → 收益确实来自桥接/覆盖特征。

**状态**：**已确立（有条件）**——候选池完整时集合选择显著优于逐候选 workspace；但 **hybrid B=2 端到端不显著**（+2.7pt，CI 重叠）。所以它作为默认选择器，但不能宣称“B=2 因此变好”。

## 4. 已推翻的结论（本档案最重要的部分）

> 这一节保留“当时为什么那么想”，以及“哪条证据推翻了它”。不删、不淡化。

### 4.1 一次性 workspace 重排是网络级增益（2026-11-06）

- **当时为什么那么想**：5 个节点各自检索，gold 分散；把候选放进容量受限的 workspace，用 verifier + novelty + coverage + coalition 竞争，理论上能比 flat ensemble 更好地保留互补证据。E1 的 NBPW 0.55 vs flat verifier 0.53 看起来支持这个想法。
- **推翻它的证据**：E1b 去掉跨节点 agreement 的公平对照只有 **+0.01，CI [0.00, 0.03]**，1 win / 0 losses；`no_novelty` 0.53、`no_coverage` 0.53，与完整版差在噪声内。verifier 的 11 维特征里 `nov` 平均 |贡献| 只有 0.22（overlap 是 1.09），`node_rel` 是恒 0.5 的死特征。
- **取代它的结论**：杠杆是 verifier 质量与节点选择，不是 workspace 规则。后续所有资源转向这两处。

### 4.2 “dense profile 能改善节点选择”（2026-11-06）

- **当时为什么那么想**：节点画像依赖词面统计；用 TF-IDF 余弦相似度做一个“稠密画像”应该能补充语义信号。
- **推翻它的证据**：`active_dense` 在 B=2/B=3 与 random **逐位相同**（0.090 / 0.217）。TF-IDF 余弦没有跨节点语义区分度，节点打分退化为常量。
- **取代它的结论**：要么用真正的句向量（11-11 的 bge），要么不要做“伪稠密”。真正的稠密画像直到 D1 才兑现。

### 4.3 “B=2 的 selector 桶 76% 是节点选择”（2026-11-09 → 2026-11-10 修正）

- **当时为什么那么想**：差距分解显示 B=2 的选择器损失 0.457，其中大部分记为 `C1 ∧ ¬C2`（池可取但节点没查）。5 节点随机切分下，这个比例确实是 75%。
- **推翻它的证据**：11-10 的深度报告在 3 个主题节点上重做分解：**只有 3pt 来自“gold 节点没被查”**（6% 的 gold 事件），其余是节点内深度（k=5 召回只有 0.665）。5 节点随机切分与 3 主题切分的结构不同，结论不能移植。
- **取代它的结论**：主题切分下先投**检索深度**，不是节点选择。这条修正直接催生了 3.6 的深度实验。

### 4.4 “NLI 可以直接给问句打分”（2026-11-09）

- **当时为什么那么想**：NLI 蕴含概率是“段落是否支持问题”的自然信号；MNLI 模型现成可用。
- **推翻它的证据**：把问句直接当 hypothesis 时，蕴含概率与 gold **负相关**（单元内 AUC **0.444**，单独排序 both@5 **0.023**，最差 gold 名次中位 19）。MNLI 的 hypothesis 必须是陈述句，问句会被当成不完整命题。
- **取代它的结论**：NLI 路线不是“没调好”，是**结构性错误**；要做必须先做问句→陈述句改写。在改写之前，NLI 不进默认。

### 4.5 “26 维融合读出应该进默认”（2026-11-09 → 2026-11-10 降级）

- **当时为什么那么想**：all-nodes 上融合读出 0.517 → 0.677（+16pt），CI 不重叠，看起来是明确的读出升级。
- **推翻它的证据**：端到端 hybrid B=2 只有 **+1.3pt**（0.390 → 0.403），而成本是 **126.8 ms/对 vs 0.97 ms/对（131×）**；多节点复现时收益衰减到 +2pt；在 replica 上因训练 head 正样本太少而崩（0.36 → 0.09）。
- **取代它的结论**：融合读出保留为 opt-in 高预算档，默认 `fast`。**“离线指标大涨、端到端不动”是这条链路反复出现的模式**，后面 rerank、k=20 都是同一个教训。

### 4.6 “混合检索优于纯稠密”（2026-11-11）

- **当时为什么那么想**：BM25 擅长词面精确匹配，稠密擅长语义；两路融合（linear / RRF）通常比单路稳。11-10 的“稀疏+稠密融合无效”被归因于当时用的是未训练编码器，所以换真编码器后应该翻盘。
- **推翻它的证据**：alpha 扫描最优落在网格边界 0.8（几乎纯稠密）；hybrid@20 0.710 < dense@20 **0.750**；RRF@20 只有 0.670。BM25 成分在两跳问题上只是噪声——第二跳证据常与问句无字面重叠，词面分只能把第一跳再抬一遍。
- **取代它的结论**：纯稠密是默认；BM25 只作为可选/兜底。

### 4.7 “rerank 是通用增益”（2026-11-10 → 2026-11-11 修正）

- **当时为什么那么想**：rerank@20 在 BM25 底上把 set 从 0.590 拉到 0.610（+25pt 相对更早的 0.360），是当时性价比最高的一档。
- **推翻它的证据**：dense@20 0.750 → dense+rerank@20 **0.690（−6pt）**；hybrid→rerank 同样 −6pt。逐句特征是为词面宽候选设计的，在语义已排好的候选上重排等于用弱信号覆盖强信号。
- **取代它的结论**：rerank 的价值是**给弱检索器补课**，不是给强检索器加分；默认关闭（`NBPW2_RERANK=0`）。

### 4.8 “加深到 k=20 更好”（2026-11-11 → 2026-11-12 定案）

- **当时为什么那么想**：dense@20 的池上限 0.810 > dense@10 的 0.780，set 0.750 > 0.740，看起来“更深更全”。
- **推翻它的证据**：走真实 `recall()` 入口的同 head 配对：k=10 set **0.720**，k=20 **0.730**，Δ **−0.01 [−0.04, 0.02]**（k=10 − k=20）；workspace 反而 +0.02。多花 ~94ms 换 0pt。更早的“.750”是 raw rank 口径，squash 开后是 .710–.720。
- **取代它的结论**：默认 k=10，k=20 保留为高预算档。**池上限高 ≠ 端到端高**；这是“pool 上限不等于接近 oracle”的第一个直接证据。

### 4.9 “多跳桥接/自适应第三跳优于独立 top-2”（2026-11-12 → 2026-11-13 定案）

- **当时为什么那么想**：`bridge_hop` 用第一跳 anchor 的实体去桥接第二跳，符合多跳题的结构；D2 在 D1 上加锚段落稠密桥接，理论上更精细；D3 在桥接弱时加第三跳，理论上更稳。
- **推翻它的证据**：D1 **0.790** > D2 0.770 > D3 0.760；D3 的 +0.04 CI **[−0.01, 0.10]** 跨零，且平均 2.19 个节点查询；B=3 时 D1 与 bridge_hop 返回同一 30 候选并集，set 都是 0.790。
- **取代它的结论**：路由的瓶颈是**打分函数**，不是跳数。最简单的独立 top-2 + 稠密 max-cosine 就拿到了最大收益。

### 4.10 “单阈值 gate 可以决定弃答”（2026-11-13）

- **当时为什么那么想**：7 例里编造例的 coverage 0.374、verifier 0.9933 看起来“高”，而空答案例的 verifier 0.896/0.995 也高；直觉上可以用一个阈值把“不可信”切出去。
- **推翻它的证据**：98 题上逐个试：`coverage<0.30` 误杀 1 道正确对照；`focus<0.30` 误杀 2 道；`verifier<0.90` 误杀 1 道；`verifier<0.70` 一道不拦（编造例正好 0.9933）；`route_top1` 几乎不触发。**编造例的信号与正确对照无法用单阈值分开。**
- **取代它的结论**：弃答必须是结构性的（空 span + grounding + route margin），不能是“置信度低就拒答”。

### 4.11 “弃答题里有相当比例是语料没有答案”（2026-11-13）

- **当时为什么那么想**：46.9% 的弃答率太高，最自然的解释是“题超出了语料覆盖”。
- **推翻它的证据**：46 道里 (a)=0；全部 46 道的 gold 支撑段都在 pool 中（`support_in_pool=True`）；37 道的 gold 字面就在选中的段落全文里。
- **取代它的结论**：这是**抽取能力问题**，不是覆盖问题。把抽取失败标成“证据不足”，等于把读出的结构性缺陷包装成“诚实的不知道”——这正是用户要求防的事。

### 4.12 “49 道弃答”（2026-11-13 被生产口径取代）

- **当时为什么那么想**：上线前用 240 字符 snippet 做 grounding，得到 49 道 `span_or_ungrounded`，弃答率 50.0%。
- **推翻它的证据**：生产三态用整段文本做 grounding，并把低 margin 单列为 conflict，同一批 98 题得到 **46 insufficient + 4 conflict = 50 非 answered**。总数接近，但**构成不同**：49 里的 3 道被重新分到 conflict（4 道 conflict 中 1 道来自原本 answered）。
- **取代它的结论**：所有引用弃答构成的地方以 46+4 为准；49 只作为“上线前估算”保留。

## 7. 下一步优先级（按“能吃到多少”排序，不按容易程度）

> “能吃到多少”用**受影响题数 / 98** 表示上限；这是覆盖率上限，不是准确率承诺。实际收益取决于读出修好后能否答对。

| 优先级 | 动作 | 直接受益题数（上限） | 占 98 | 依据 | 风险 / 备注 |
|---|---|---:|---:|---|---|
| **P0** | 给读出加 `other` 分支（实体/名词短语抽取） | **19** | 19.4% | b1a 19 道，gold 字面已在选中全文 | 需要实体 grounding，否则会把“段内任意名词”当答案；可能引入新的编造 |
| **P1** | 加 yes/no 判定分支 | **8** | 8.2% | b3 8 道，两段证据都在选中 | 需要比较/属性判断，不是纯抽取；可用 NLI（但必须先做问句→陈述句改写） |
| **P2** | 修 span 选择（日期区间、数字格式、错误段落） | **10** | 10.2% | b1b 10 道，其中 7 道抽到别的值、3 道空 | 需要更强的答案侧打分/答案类型约束；不改检索 |
| **P3** | 加深/改进支撑段选择 | **9** | 9.2% | b2 9 道，支撑段未进 K=5 | 收益最小；D1 后 node-not-queried 只剩 1%，主要是深度 |
| **P4** | 冲突检测扩展到同实体多值 | **4** | 4.1% | 4 道 conflict；当前只按 route margin<0.02 | 会把更多题移出 answered；需要“并列展示”而不是“选一个” |
| **P5** | 跨节点路由/更多节点 | **≤33 题相关** | — | 只有 33 题跨节点；D1 已将 node recall 抬到 0.995 | 样本太小，无法支撑结论；不建议现在投 |
| **P6** | 融合读出 / rerank / 更大 k | ~0 | — | 端到端 +1.3pt / −6pt / −1pt；131× / 负 / 0 | **不建议**；这些是“离线涨、端到端不动”的典型 |

**排序理由**：
- P0+P1 合计 27 题（27.6%），是唯一能同时解释“46 道弃答”和“读出无分支”的大块；它们都不需要改检索/路由，属于当前链路的空缺，而不是新能力。
- P2 的 10 题需要改答案侧打分，收益明确但比 P0/P1 小。
- P3 只有 9 题，且 D1 后检索已不是主瓶颈；放在 P2 之后。
- P4 只有 4 题，且会降低覆盖率；放在读出修好之后再做，否则会把“读出失败”误判成“冲突”。
- P6 是负 ROI，明确不建议。

**不建议现在做的**：50 节点 WAN、更大模型读出（894MB 上限）、把 fusion/rerank 拉回默认、用单阈值 gate 替代结构性三态。

## 8. 限制与不确定

1. **98 题样本偏小**。整体 7/98 的 95% CI 是 [3.5%, 14.0%]，和旧链路 8/98 的 [4.2%, 15.3%] 大幅重叠；**不能声称三态让准确率显著下降或上升**。answered 子集 7/48 的 CI 是 [7.2%, 27.2%]，同样很宽。
2. **跨节点只有 33 题**。所有“路由/冲突/跨节点”的结论都受这 33 题限制；D1 的 +0.07 虽然 CI 不含零，但其中跨节点子集的样本更小，不能单独下结论。
3. **894MB 内存是硬上限**。VPS 常驻 500–600MB，加 2G swap；这排除了更大的读出模型、更大的 rerank 模型、更多节点缓存。任何“上大模型”的方案在当前部署上不可行。
4. **pool 上限不等于接近 oracle**。dense@20 的 ceiling 0.810、D1 的 0.880，但端到端只有 0.790；池上限抬升多次没有转化为端到端（k=20、B=3、D2/D3 都是例子）。**“上限高”只说明还有空间，不说明已经接近 oracle。**
5. **both@5 与 exact-match 的样本不同**：0.790 用 100 题，7.1% 用 98 题（2 道 >180 字符被线上接口拒绝）。两者不能直接相除或相减。
6. **12 例核对是抽样，不是全量**。46 道的分类是逐题审计（脚本 + 规则），但 12 例的人工理由只覆盖抽样；剩余 34 道的分类依赖 `class_reason` 规则，可能有个别边界错分。
7. **7 例测试集是构造的**。它覆盖桥接断裂、答案段缺失、前提错误、冲突、对照，但不是自然分布；`fabricated 0` 只说明这 7 例被拦住，不说明所有编造都被消除。
8. **数据只来自 HotpotQA validation 子集**，3 个主题节点，不是真实地理分布式网络；LAN 实验只有 25 题，且是方向性结果。
9. **exact-match 是严格口径**：先剥离非数字字符再比，但没有做同义词/短语归一；`about 450,000` vs `450,000` 这类差异会被算错。真实产品口径可能更宽。
10. **延迟数据分三种测量条件**（空载本机 / 演示 trace / VPS 生产），不能直接比较；VPS 的 89–431ms 波动主要来自 2 vCPU 争用和冷启动。
11. **“已确立”不等于“已发表”**：所有 CI 都来自本项目内部的配对 bootstrap 或 Wilson，没有独立复现；唯一的多数据集复现是 E9 的 250 题与 E12 的主题切分。
